<Statement>

Given the heads of two sorted linked lists, merge them into one sorted list by **splicing the
existing nodes** together, and return the new head.

<Examples>
  <Example input={`list1 = [1, 2, 4]
list2 = [1, 3, 4]`} output={`[1, 1, 2, 3, 4, 4]`}>
    Equal values are both kept — this is a merge, not a union.
  </Example>
  <Example input={`list1 = []
list2 = [0]`} output={`[0]`}>
    One side may be empty, and the answer is simply the other side.
  </Example>
  <Example input={`list1 = []
list2 = []`} output={`[]`}>
    Both empty is legal too.
  </Example>
</Examples>

<Constraints>

- Each list holds between `0` and `50` nodes
- `-100 <= Node.val <= 100`
- Both lists are sorted in **non-decreasing** order

</Constraints>

</Statement>

<Signals>

- Both inputs are sorted, so the next value of the answer is always one of **two candidates**: the
  head of one list or the head of the other. That is a comparison, not a search.
- "Splicing the nodes together" rules out building a new list of values. The nodes move; nothing is
  copied.
- The result's head is whichever list starts smaller — a case distinction that disappears entirely
  once you build the answer behind a placeholder node.

</Signals>

<BruteForce>

Collect every value from both lists, sort them, and build a fresh list.

**O((m + n) log(m + n)) time, O(m + n) space.** Correct, and it throws away the fact that both
inputs were already sorted — the one thing the problem gave you. The bottleneck is the sort: the
merge step alone is linear, and sorting re-derives an ordering that already existed.

</BruteForce>

<Insight>

Build the answer behind a throwaway head node, and appending the smaller of the two fronts never needs a special case.

</Insight>

<Approach>

1. Create a `dummy` node that is not part of the answer, and a `tail` pointer starting at it.
2. While both lists still have a node, append the smaller head to `tail` and advance that list.
3. Move `tail` to the node just appended.
4. When one list runs out, append **all** of the other — it is already sorted, so nothing more is
   needed.
5. Return `dummy.next`.

The dummy is the whole trick. Without it, the first append has to decide *"is this the head of the
result?"* on every iteration, or be special-cased before the loop. With it, `tail.next = node` is
uniformly correct from the very first step.

</Approach>

<Solution variant="brute">

```python
class Solution:
    def mergeTwoLists(self, list1: Optional[ListNode], list2: Optional[ListNode]) -> Optional[ListNode]:
        # O((m + n) log(m + n)) time, O(m + n) space
        values = []
        for node in (list1, list2):
            while node:
                values.append(node.val)
                node = node.next

        dummy = ListNode()
        tail = dummy
        for value in sorted(values):
            tail.next = ListNode(value)
            tail = tail.next

        return dummy.next
```

</Solution>

<Solution variant="optimal">

```python
class Solution:
    def mergeTwoLists(self, list1: Optional[ListNode], list2: Optional[ListNode]) -> Optional[ListNode]:
        # O(m + n) time, O(1) space — the nodes are spliced, not copied
        dummy = ListNode()
        tail = dummy

        while list1 and list2:
            if list1.val <= list2.val:
                tail.next = list1
                list1 = list1.next
            else:
                tail.next = list2
                list2 = list2.next
            tail = tail.next

        tail.next = list1 or list2      # whatever is left is already sorted

        return dummy.next
```

</Solution>

<Pitfalls>

- **`tail.next = list1 or list2` is not optional.** Dropping it silently truncates the answer at the
  point where the first list ran out. It also handles both-empty correctly, since `None or None` is
  `None`.
- Use `<=`, not `<`, when comparing heads. Either produces a sorted list, but `<=` keeps equal values
  in their original relative order, which is what "stable" means and what a follow-up will ask about.
- The dummy node is never returned. Returning `dummy` instead of `dummy.next` prepends a phantom `0`
  to every answer — a classic and very visible bug.
- Do not build new nodes. `O(1)` space is only true because the existing nodes are relinked; a
  version that allocates is `O(m + n)` and should be described as such.

</Pitfalls>

<FollowUps>

- *"Merge k lists instead of two."* — Problem 6.10 in this category. Merging them pairwise turns
  `O(N · k)` into `O(N log k)`, and this function is the inner step.
- *"Do it recursively."* — `merge(a, b)` returns the smaller head with its `next` set to
  `merge(rest, other)`. Very short, and `O(m + n)` stack.
- *"What if the lists were sorted descending?"* — Flip the comparison. Nothing else changes, which is
  a good sign the structure is right.

</FollowUps>
