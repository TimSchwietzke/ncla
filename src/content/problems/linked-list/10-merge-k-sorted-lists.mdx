<Statement>

Given an array of `k` sorted linked lists, merge them all into one sorted list and return its head.

<Examples>
  <Example input={`lists = [[1, 4, 5], [1, 3, 4], [2, 6]]`} output={`[1, 1, 2, 3, 4, 4, 5, 6]`}>
    Three sorted lists, eight nodes, one sorted result.
  </Example>
  <Example input={`lists = []`} output={`[]`}>
    No lists at all — the answer is empty, and the code must not index into nothing.
  </Example>
  <Example input={`lists = [[]]`} output={`[]`}>
    One list, and it is empty. Different from the case above, and just as easy to crash on.
  </Example>
</Examples>

<Constraints>

- `k == lists.length` with `0 <= k <= 10^4`
- `0 <= lists[i].length <= 500` and `-10^4 <= lists[i][j] <= 10^4`
- Every list is sorted ascending; the total number of nodes is at most `10^4`

</Constraints>

</Statement>

<Signals>

- Merging **two** sorted lists is already solved. The only question is how to apply it `k - 1` times
  without paying for it `k - 1` times.
- Folding them one at a time makes the accumulated list longer on every merge, so early nodes get
  re-walked again and again — that repetition is the cost to attack.
- Pairing the lists instead halves their count per round, so every node takes part in `log k` merges
  rather than `k`. Same total merges, a completely different amount of walking.

</Signals>

<BruteForce>

Merge list 1 into the result, then list 2, then list 3, and so on.

**O(N · k) time, O(1) space** for `N` nodes in total. Correct and tempting, because it reuses the
two-list merge directly. The bottleneck is that the accumulated result is walked on every single
merge: after `i` rounds it already holds most of the nodes, and round `i + 1` walks them all again.

</BruteForce>

<Insight>

Merge the lists in pairs rather than one after another, and every node passes through log k merges instead of k.

</Insight>

<Approach>

1. If there are no lists, return `None`.
2. While more than one list remains, walk the array **two at a time**, merging each pair into one
   list and collecting the results.
3. A leftover odd list carries over untouched — `lists[i + 1] if i + 1 < len(lists) else None`, and
   merging with `None` is already handled.
4. Replace the array with the merged round and repeat.
5. One list remains: return it.

The two-list merge is the same dummy-head loop as problem 6.2. Nothing new is written here; the whole
gain comes from the order in which it is applied.

The heap alternative has the same complexity: push the `k` heads into a min-heap, pop the smallest,
append it, and push its successor. It costs `O(k)` space instead of `O(1)`, and in Python it needs a
tiebreaker in the tuple, because `ListNode` objects cannot be compared.

</Approach>

<Solution variant="brute">

```python
class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        # O(N * k) time, O(1) space
        def merge(a: Optional[ListNode], b: Optional[ListNode]) -> Optional[ListNode]:
            dummy = ListNode()
            tail = dummy
            while a and b:
                if a.val <= b.val:
                    tail.next, a = a, a.next
                else:
                    tail.next, b = b, b.next
                tail = tail.next
            tail.next = a or b
            return dummy.next

        result = None
        for node in lists:
            result = merge(result, node)
        return result
```

</Solution>

<Solution variant="optimal">

```python
class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        # O(N log k) time, O(1) space beyond the round bookkeeping
        if not lists:
            return None

        def merge(a: Optional[ListNode], b: Optional[ListNode]) -> Optional[ListNode]:
            dummy = ListNode()
            tail = dummy
            while a and b:
                if a.val <= b.val:
                    tail.next, a = a, a.next
                else:
                    tail.next, b = b, b.next
                tail = tail.next
            tail.next = a or b            # merging with None is free
            return dummy.next

        while len(lists) > 1:
            merged = []
            for i in range(0, len(lists), 2):
                first = lists[i]
                second = lists[i + 1] if i + 1 < len(lists) else None
                merged.append(merge(first, second))
            lists = merged                # each round halves the count

        return lists[0]
```

</Solution>

<Pitfalls>

- **`lists` may be empty, and it may hold empty lists.** `[]` and `[[]]` are different inputs and both
  legal. Returning `lists[0]` without the `if not lists` guard raises `IndexError` on the first.
- **Guard the odd list with `i + 1 < len(lists)`.** With an odd count, the last pair has no partner,
  and merging against `None` is exactly the right behaviour — but only if you pass `None` rather than
  indexing past the end.
- Merging one at a time is `O(N · k)`, not `O(N log k)`. Both are "merge repeatedly"; only the order
  differs, and the complexity claim is what the interviewer checks.
- **In Python a heap of nodes needs a tiebreaker.** `heappush(heap, (node.val, node))` raises
  `TypeError` as soon as two values tie, because it then tries to compare the nodes. Push
  `(node.val, index, node)` instead.
- `k` can be `10^4` while the total node count is also `10^4`, so most lists are empty. The pairing
  loop handles that without special cases; a heap version should skip empty heads when seeding.

</Pitfalls>

<FollowUps>

- *"Use a heap instead."* — Same `O(N log k)`, `O(k)` space, and it is the better shape when the lists
  arrive as a stream rather than as an array. Say the tiebreaker detail; it is the thing that bites.
- *"Merge k sorted **arrays**."* — Identical structure, and the pairing version becomes exactly the
  merge phase of merge sort.
- *"Why is pairing `log k` rounds?"* — Each round halves the number of lists, and every node is
  copied once per round. `N` work per round times `log k` rounds is the bound.

</FollowUps>
