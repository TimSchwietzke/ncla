<Statement>

Given `preorder` and `inorder`, the two traversals of the **same** binary tree with **unique** values,
reconstruct the tree and return its root.

<Examples>
  <Example input={`preorder = [3, 9, 20, 15, 7]
inorder = [9, 3, 15, 20, 7]`} output={`[3, 9, 20, null, null, 15, 7]`}>
    Preorder names the root first: 3. In inorder, everything left of the 3 is its left subtree.
  </Example>
  <Example input={`preorder = [-1]
inorder = [-1]`} output={`[-1]`}>
    A single node. Both traversals are the same one-element list.
  </Example>
  <Example input={`preorder = [1, 2, 3]
inorder = [3, 2, 1]`} output={`[1, 2, null, 3]`}>
    A chain leaning entirely left — inorder reversed is the tell.
  </Example>
</Examples>

<Constraints>

- `1 <= preorder.length <= 3000` and `inorder.length == preorder.length`
- `-3000 <= preorder[i], inorder[i] <= 3000`
- All values are **unique**, and both arrays are traversals of the same tree

</Constraints>

</Statement>

<Signals>

- **Preorder visits the root first.** So `preorder[0]` is the root, with no searching required — that
  is the entire foothold.
- **Inorder visits the left subtree, then the root, then the right.** So finding the root's position
  in `inorder` splits the remaining values into exactly the two subtrees, and gives their **sizes**.
- Values are unique, which is what makes "find the root in inorder" well defined. Without that
  guarantee the reconstruction is not unique either.

</Signals>

<BruteForce>

Recurse on **slices**: take `preorder[0]` as the root, find it in `inorder` with `list.index`, then
build the left subtree from `preorder[1:mid+1]` and `inorder[:mid]`, and the right from the rest.

**O(n²) time, O(n²) space.** It reads beautifully and it is how the idea should first be explained.
The bottleneck is doubled: `index` is a linear scan at every node, and every slice copies its portion
of both arrays. On a degenerate tree that is quadratic in both.

</BruteForce>

<Insight>

Preorder hands you the root; inorder tells you how many nodes go left, which is all the recursion needs.

</Insight>

<Approach>

1. Build a dictionary from **value → index in `inorder`**, once. That replaces every `list.index` with
   an `O(1)` lookup.
2. Keep a single moving pointer into `preorder`. Because preorder builds root, then the whole left
   subtree, then the whole right subtree, consuming it strictly left to right is exactly correct.
3. Define `build(left, right)` over a range of `inorder`:
4. If `left > right`, the range is empty — return `None`.
5. Take the next value from `preorder` as this node, and look up its position `mid` in `inorder`.
6. Build the **left** child from `(left, mid - 1)` first, then the right from `(mid + 1, right)`.

Step 6's ordering is not cosmetic. The shared preorder pointer only lines up if the left subtree is
consumed before the right, because that is the order preorder wrote them in.

</Approach>

<Solution variant="brute">

```python
class Solution:
    def buildTree(self, preorder: list[int], inorder: list[int]) -> Optional[TreeNode]:
        # O(n^2) time, O(n^2) space — a scan and two copies at every node
        if not preorder:
            return None

        root = TreeNode(preorder[0])
        mid = inorder.index(preorder[0])

        root.left = self.buildTree(preorder[1:mid + 1], inorder[:mid])
        root.right = self.buildTree(preorder[mid + 1:], inorder[mid + 1:])

        return root
```

</Solution>

<Solution variant="optimal">

```python
class Solution:
    def buildTree(self, preorder: list[int], inorder: list[int]) -> Optional[TreeNode]:
        # O(n) time, O(n) space
        position = {value: i for i, value in enumerate(inorder)}
        self.next_root = 0                   # preorder is consumed strictly left to right

        def build(left: int, right: int) -> Optional[TreeNode]:
            if left > right:
                return None

            value = preorder[self.next_root]
            self.next_root += 1
            node = TreeNode(value)

            mid = position[value]
            node.left = build(left, mid - 1)   # left FIRST: that is preorder's own order
            node.right = build(mid + 1, right)

            return node

        return build(0, len(inorder) - 1)
```

</Solution>

<Pitfalls>

- **Build the left subtree before the right.** The shared preorder pointer encodes the traversal
  order; swapping the two lines silently constructs a mirrored tree, and on a symmetric test it looks
  fine.
- **`list.index` inside the recursion is what makes the naive version quadratic.** The dictionary is
  the whole optimisation, and it is one line. Say the bound before you write it.
- Slicing is the *other* half of the quadratic cost, and it is easy to miss because it looks free.
  Passing index ranges instead of subarrays is what makes the space `O(n)` rather than `O(n²)`.
- The uniqueness guarantee is load-bearing. With duplicates, `position` would collide and the
  reconstruction would not even be unique — worth saying, because it explains why the constraint is
  there.
- `preorder` and `postorder` alone do **not** determine a binary tree. Inorder is the one that splits;
  the pairing matters, not just having two traversals.

</Pitfalls>

<FollowUps>

- *"From inorder and postorder instead."* — LC 106: postorder's **last** value is the root, so consume
  it right to left and build the **right** subtree first. Same idea, mirrored.
- *"From preorder and postorder."* — LC 889: no longer unique, because a node with one child cannot be
  told apart. Any valid answer is accepted, which is the giveaway that information is missing.
- *"Avoid the recursion."* — An iterative version with a stack exists and is genuinely harder to
  follow. Worth knowing it exists; not worth leading with.

</FollowUps>
