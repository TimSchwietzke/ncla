<Statement>

A node `X` is **good** if no node on the path from the root down to `X` holds a value greater than
`X`. Return how many good nodes the tree has.

<Examples>
  <Example input={`root = [3, 1, 4, 3, null, 1, 5]`} output="4">
    Good: the root 3, the left 3 (nothing above it beats 3), the 4, and the 5. The 1s are not.
  </Example>
  <Example input={`root = [3, 3, null, 4, 2]`} output="3">
    The root 3, its child 3 (equal is allowed — "greater", not "at least"), and the 4.
  </Example>
  <Example input={`root = [1]`} output="1">
    The root is always good: its path is just itself.
  </Example>
</Examples>

<Constraints>

- The tree holds between `1` and `10^5` nodes
- `-10^4 <= Node.val <= 10^4`

</Constraints>

</Statement>

<Signals>

- The condition is about the **path from the root**, so the information flows **downwards**. Every
  problem so far reported upwards; this one carries a value down and returns a count back.
- Everything on that path collapses to a single number — the **maximum so far**. Nothing else about
  the path matters, which is what keeps this `O(1)` state per level.
- "No node greater than X" means equal values are still good. That word is the whole of the second
  example.

</Signals>

<BruteForce>

For every node, walk back up to the root and check whether anything on the way is larger.

**O(n · h) time, O(h) space** — and there is no parent pointer, so in practice you would collect the
path on the way down anyway. The bottleneck is that the maximum along the path is recomputed for
every node, although it changes by at most one comparison per step.

</BruteForce>

<Insight>

The whole path from the root collapses to one number — its maximum — so carry that down and compare against it.

</Insight>

<Approach>

1. Define `walk(node, best)` where `best` is the largest value seen on the path so far.
2. An empty node contributes `0`.
3. This node is good when `node.val >= best`.
4. Recurse into both children with `max(best, node.val)`.
5. Return this node's contribution plus both children's counts.

Start the recursion with `best = root.val`, so the root is good by definition — or with negative
infinity, which amounts to the same thing and needs no non-empty check first.

</Approach>

<Solution variant="brute">

```python
class Solution:
    def goodNodes(self, root: TreeNode) -> int:
        # O(n * h) time, O(h) space — re-examines the whole path at every node
        total = 0

        def walk(node: Optional[TreeNode], path: list[int]) -> None:
            nonlocal total
            if not node:
                return
            if all(value <= node.val for value in path):
                total += 1
            path.append(node.val)
            walk(node.left, path)
            walk(node.right, path)
            path.pop()

        walk(root, [])
        return total
```

</Solution>

<Solution variant="optimal">

```python
class Solution:
    def goodNodes(self, root: TreeNode) -> int:
        # O(n) time, O(h) space
        def walk(node: Optional[TreeNode], best: int) -> int:
            if not node:
                return 0

            good = 1 if node.val >= best else 0
            best = max(best, node.val)

            return good + walk(node.left, best) + walk(node.right, best)

        return walk(root, root.val)
```

</Solution>

<Pitfalls>

- **`>=`, not `>`.** The statement says *no node greater than X*, so a value equal to the running
  maximum is still good. The second example returns 2 instead of 3 with a strict comparison.
- **Carry the maximum down, do not report it up.** This is the first problem in the category where
  the state flows the other way, and reusing the "report upwards" habit here produces a solution that
  counts something else entirely.
- Update `best` **after** testing the current node, or every node compares against itself and they all
  come out good.
- Start with `root.val`, or with `float("-inf")`. Starting with `0` is wrong the moment the tree holds
  negative values, which the constraints allow.
- The path-collecting version must `pop()` on the way back up. Forgetting it leaks siblings into each
  other's paths — the classic backtracking bug, showing up here early.

</Pitfalls>

<FollowUps>

- *"Return the good nodes themselves, not the count."* — Collect `node.val` instead of adding 1. The
  structure is unchanged.
- *"Count nodes where the path maximum is **strictly** less."* — Flip to `>`. Worth doing once, to
  feel how much a single character in the statement is worth.
- *"Path sums instead of path maxima."* — LC 112 / 113: carry a running sum down the same way. The
  pattern is identical, and recognising that is the point of this problem.

</FollowUps>
